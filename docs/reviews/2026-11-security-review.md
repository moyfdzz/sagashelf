# Security review, November 2026 (SAG-29, part 1)

Status: first part. The threat model of [ADR-006](../adr/006-security-model.md) was checked against the code, and the OWASP ASVS level 2 chapters were walked one by one. Each gap is a **finding** with a severity and ends as a ticket. Nothing here changes behavior.

## How it was made, and what it did not cover

Measured on `main` at `6fdd92e` (2026-11-04), by reading the code and the configuration, and by running searches over `app/`, `server/`, `workers/` and `db/` (`dangerouslySetInnerHTML`, `eval`, `sql.raw`, `z.object` against `z.strictObject`, `redirect(`, `Access-Control`, every `console.*` call), `npm audit`, and the file `wrangler.jsonc`.

**Not covered here, and where it goes:**

- It is a walk by **chapter** of ASVS 4.0.3, not a check of each of its requirements one by one, and it is not a penetration test. Nothing was attacked, in production or anywhere else.
- The authorization of the **reads** was part 2 of SAG-29 and is done: see "Part 2: who can read what" below. The writes are covered since SAG-128 (`app/routes/write-actions.test.ts`).
- What the logs print, the inventory of secrets and the rotation plan were part 3 and are done: see "Part 3: logs, secrets and scans" below and [secrets](../secrets.md). The incident plan is part 4 and is done: [incident plan](../incident-plan.md).
- What only the owner can do: the restore of Neon on a branch, the scripted burst against `sagashelf.app`, and a check of the Clerk protections in the **Production** instance (the settings in [edge-setup](../edge-setup.md) were written for the Development one). They are listed at the end.
- Clerk and Cloudflare are trusted for what they do (credentials, sessions, the edge). Only how this code uses them was read.

## Part 2: who can read what

`app/routes/read-loaders.test.ts` has one row for each of the 37 routes with a `loader`, with the kind of access it has, and it fails for a route that is not in the table. The kinds: **9 session** pages (the library, an entry, the inbox, recommendations, statistics and four settings pages), **2 administration** pages, **5 pages for visitors** that show a little more to a person who is signed in (a profile and its lists, a title, a saga, the search), **12 public** routes that never ask who is reading, and **9 form targets** that answer a `GET` with 405 or send it home.

What it proves, and how:

- A session page stops at the session, before it opens the database. An administration page asks for the role `admin` and stops there for anybody else. Both were proven with mutations: removing the guard, moving it after the database, and asking for a weaker role are all caught.
- For the pages for visitors and the public ones, the loaders read public data before they ask who is looking, so a run against a failing database never reaches the guard. The test reads the source instead: a visitor page must call `getOptionalUser` and must not call `requireRole` (or `requireUser`, unless the file also has an `action`); a public route must call none of the three. Making a visitor page demand a session is caught. Making a public route ask for a session was **not** tried with a mutation.
- What one person may see of another is not re-tested here. It is decided by `canView`, which has no exception for an administrator (an administrator who reads a profile is a stranger), and it is proven on the real database for every level and every relationship (`db/social-profile.integration.test.ts`), with the privacy of each person on a list (`db/social.integration.test.ts`), and in what each profile route asks of it (`u.$username.test.ts`, `u.$username.$kind.test.ts`). The data of one person never reaching another (library, statistics, notifications, recommendations, webhooks) has its own integration tests per area.
- It proves the code against mocks of the session and the database, not against Clerk. No new finding came out of it.

## Part 3: logs, secrets and scans

**What the logs print.** Every `console.*` call in `app/`, `server/` and `workers/` was read. Our own calls write an event name, the **name** of an error (never its message) and counts: the title page, the header, the search, the jobs of the crons, the Clerk webhook (the Svix id, the type of event and the name of the error), the deletion of an account and the change of a username. What a delivery of a webhook stores as `last_error` is a short code (`timeout`, `network`, `redirect`, `http_<status>`) and nothing from Discord's answer. The exception was S-6: what React Router logged by itself, and the direct `console.error(error)` of the stream of `entry.server.tsx`. It was fixed in SAG-134 (see below). The `console.error` of `entry.client.tsx` runs in the visitor's browser and reaches no log of ours.

**Error responses.** A refusal answers a short code (`forbidden`, `invalid_request`, `rate_limited`), the pages show a generic message in production, and the Clerk webhook says nothing about why it refused. No message of an error goes into a response: the matches of `.message` in the code are codes of Zod issues and the message that only the development server shows.

**Not looked at.** The request logs that Cloudflare itself keeps for the Worker (they include the URL), and how long Cloudflare keeps the logs.

**Secrets.** [`docs/secrets.md`](../secrets.md) has the inventory by name (what each is, where it lives, what reads it, what breaks if it is wrong) and how to rotate each one. One of the five secrets is read by no code (`TURNSTILE_SECRET_KEY`, SAG-132). The repository has no Actions secrets, and `.gitignore` covers `.env*`, `.dev.vars*`, `*.pem`, `*.key`, `id_rsa*`, `credentials*.json`, `CLAUDE.local.md` and `.claude/settings.local.json`; the only tracked file with such a name is `.env.example`.

## Part 4: the incident plan, and where the ticket stands

[`docs/incident-plan.md`](../incident-plan.md) has the order that works for any incident, a table of levers from the smallest to the largest (pause the webhooks with `WEBHOOKS_ENABLED`, turn a provider off, close sign-ups in Clerk, slow an attack, stop one person, roll back a deployment, take the site off), five scenarios in numbered steps (a leaked secret, which includes a leaked webhook address; the administrator account; a wave of fake sign-ups; a bad deployment; lost data), how to restore Neon, and the burst for M-2.

What was verified and what was not: the effect of `WEBHOOKS_ENABLED`, the erasure that follows `user.deleted` and the idempotency table that a restore brings back were read in the code. The facts of Neon, Clerk and Cloudflare come from their documentation, read on 2026-11-04, and are written in the plan with that date; the click path of each dashboard was **not** shown by those pages. The two PowerShell snippets were run against a local server that answers 200, 303 and 429 (they count correctly) and **not against production**. No lever was pulled and nothing was restored: **the plan has never been used for real.**

| S-1 | Medium   | **`/media/open` is a `GET` that writes, and anyone can call it.** A title that is not saved yet is fetched from a provider and stored. It needs no session and no `Origin` (a `GET` has none), and its only limit is the search limiter (60 a minute per IP address and per Cloudflare location). Accepted, with the reason:

- **24 vulnerabilities in `npm audit`, 9 of them high, all in development tools** (`@lhci/cli` and what it pulls in: Lighthouse, Puppeteer, `proxy-agent`, `body-parser`, `basic-ftp`). `npm audit --omit=dev` finds 0. None of it is in the Worker or is run on user input. Dependabot lists no open alert on 2026-11-04 (the one about `minimatch`, kept open on purpose, is not listed any more). The ones that matter are the ones in production, which S-2 makes a rule.
- **The rate limit is approximate**: it counts per Cloudflare location and is eventually consistent (ADR-011). It slows abuse down and is not a quota.
