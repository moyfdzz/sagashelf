# ADR-050: The analytics collector writes straight to Postgres, with a daily salt

- **Status:** Accepted
- **Date:** 2026-11-12
- **Implementation:** Partial (SAG-24: everything is built and the privacy text is written, but it is not switched on: the owner turns off Cloudflare Web Analytics and sets `ANALYTICS_ENABLED`, edge setup section 16. This becomes Done when it is on and checked)
- **Tickets:** SAG-24

## Context

[ADR-009](009-analytics-cookieless.md) decided on cookieless, first-party analytics and left three things open: where the events are kept so the database can sleep, how the visitor hash gets its daily salt, and whether the city is worth storing. This ADR settles them for the first part of SAG-24, the collector.

## Decision

- **One row per event, straight to Postgres.** `/api/collect` validates the event and inserts one row into `analytics_events`. There is no buffer between the two. The cost is known from ADR-009: a write keeps the Neon compute awake, and the Free plan has 100 compute hours a month (read 2026-10-21, see ADR-009). With the traffic of a personal portfolio the database still sleeps between visits. The real compute hours are watched for a few weeks after the tracker ships; if the database no longer sleeps, a buffer goes in its own ticket and its own ADR, after reading the limits of the service it would use.
- **The salt of the day lives in the database.** `analytics_salts` holds one random value per UTC day. The first request of the day stores it and the rest read it; the statement also deletes the salts older than yesterday, so a hash of an earlier day cannot be recomputed from anything that is kept. No Workers secret is needed. Each isolate keeps the salt of the day in memory, so most events cost one statement.
- **The visitor is the first 128 bits of SHA-256 over the salt, the address and the browser name**, in hex. The address and the browser name are read in the Worker, hashed and dropped: no column holds them (a test asserts the table has no column for an address, a city, a user or a browser name).
- **Place: country and region only.** The city is not stored. The privacy of the visitor is the reason: with a small city, "city + day + browser" comes close to naming a person, and with the low traffic of the site a count per city would be a handful. A city can be added in a ticket of its own, with its text in the privacy policy. Cloudflare gives `request.cf.country` (two letters) and `request.cf.region` (the name of the first-level region); both are `string | null` and the page says no more about when they are missing (<https://developers.cloudflare.com/workers/runtime-apis/request/>, read 2026-11-12, last updated by Cloudflare on 2026-11-02). `XX` and `T1` are not described there and are not kept.
- **What an event holds:** the kind, the path (no query string, no fragment), the visitor hash, and by kind: milliseconds of a visible tab, the type of a search (never its text), the class and host of the referrer (never its path or query), the three UTM values, the country, the region and mobile or desktop, and (SAG-254) for the speed of a load up to three numbers: LCP, CLS and INP.
- **Order of the checks:** only `POST`, size and `Origin`, rate limit, Do Not Track, Global Privacy Control, robots and a request without the address Cloudflare sets (answered as if counted, nothing kept), then the body. The robots filter uses `isbot` plus the names of headless browsers and Lighthouse; a request with no browser name is not counted. Without `CF-Connecting-IP` there is no visitor to tell apart, so nothing is kept.
- **The salt is pruned by the clock of the database,** not by the day the Worker says, so a Worker with a wrong clock cannot delete the salt other Workers still use.
- **Its own rate limit,** `COLLECT_LIMITER`, 60 a minute per caller. A visitor sends a page view and a time on page for every page, and the 30 a minute of the write endpoints would drop events of a person who browses fast.
- **Every answer is empty** (`204`, or the error status) and uncached, because `sendBeacon` ignores it.

## Alternatives considered

- **A buffer in front of Postgres** (a Cloudflare queue or store, flushed by the Cron handler). It lets the database sleep with heavy traffic, but it adds a service, limits not yet read and a place where events can be lost. Not now; the cost of writing straight is measured first.
- **Counters in the memory of the Worker.** An isolate is recycled at any moment and the counts would be lost. Rejected.
- **The salt as a Workers secret.** It needs a rotation job and a secret to keep. The table does it with the one statement that already runs. Rejected.
- **Storing the city.** Possible, not illegal by itself (the Mexican personal data law, in force since 2025-03-20, defines personal data as information about an identified or identifiable person: article 2, fr. V, read 2026-11-12 on <https://www.ordenjuridico.gob.mx/Documentos/Federal/html/wo125102.html>), but it makes "no personal data" harder to defend and it adds little for a site with few visits. Left for a later ticket.

## Consequences

**Good**

- Traffic can be counted without cookies, an address or a user id in the table.
- Nothing new to run: one table, one route, no secret, no job yet.

**Costs and risks**

- Every counted event is a database write. If traffic grows, the Neon compute hours are the limit to watch (ADR-009).
- **A public beacon can be forged.** The collector refuses a page of another site (`Origin`) and limits each caller, but anyone can send events from a script, and the events of the funnel (`signup`, `add_to_library`, `follow`) have no server-side proof that they happened. The numbers are a measure of use, not an audit; the figures that must be exact (users, entries, follows) come from their own tables in the admin dashboard (SAG-26).
- A visitor on two days counts as two, and a visitor who changes browser or network counts as two on the same day. Counting without cookies is approximate.
- Two requests of the first moment of a day can both miss the salt: the first call returns nothing and the route asks once more.
- The new rate limit is a change of `wrangler.jsonc` and needs its own namespace ids.
- The migration is applied by hand in production (`0033`). Until it is, the collector answers 500 and the tracker (next pull request) is not shipped, so nothing is lost.

## Amendment: the tracker (SAG-24, 2026-11-12)

Decided with the owner when the tracker was built. It changes two things the text above (and ADR-009) said.

- **A switch, off by default.** `ANALYTICS_ENABLED` (a plain variable, unset in CI and in previews) decides whether the pages load the tracker. The owner turns it on only after the privacy policy describes what is measured, so nothing is measured before the text says so. `e2e/analytics-off.spec.ts` fixes the default: no public page calls the collector.
- **The events of the funnel are written by the server, not by the browser.** Adding to the library and following are recorded inside their own actions, only when the action worked, so they cannot be forged from a script and an ad blocker cannot cut them. The tracker in the browser sends the page view, the time on the page and the type of a search. This replaces the ADR-009 line that has the tracker send the funnel. Built: `recordFunnelEvent` (`server/analytics/funnel.ts`) is called by `library.add`, `library.add-external` (add to library) and by the profile action when `followUser` answers `followed` (a request to a Private profile is not a follow yet, and repeating the button on a person already followed counts again, since the data function answers `followed` for both). The write runs after the answer (`waitUntil`), a failure is logged without values and never reaches the person, and the event carries the address of the action (`/library/add`, `/library/add-external`, `/u/:username`), since the server does not know the page the person was on. It follows the same rules as the collector, written once in `isMeasured` (`server/analytics/measure.ts`, on top of `canMeasure`): nothing where the switch is off, for Do Not Track, Global Privacy Control, robots, a call without `CF-Connecting-IP`, or an administrator. The whole of `recordFunnelEvent` is guarded, since the action it sits in has already been done. The collector now checks the switch too, so with it off nothing is kept even from someone who writes to it directly. Signing up is not an event: the number of accounts comes from the `users` table for the admin dashboard (SAG-26).
- **The owner is not measured when signed in as an administrator.** The root loader already knows the role, so it tells the page not to load the tracker. Nothing is kept in the browser (no cookie, no storage); a visit with no session is measured.
- **A page is a kind of page, not an address.** The tracker sends `/u/:username`, `/sagas/:slug` or `/:splat` (an address nobody wrote a page for), so the name of a person, the slug of a title and a mistyped address never leave the browser. Values from a short list we wrote (the type of a title, a list kind, a status) stay as they are, to count by type.
- **Of the referrer only the site travels** (`https://www.google.com`, not the path or the query), and a move between our own pages is sent as our own origin. The collector still keeps only its class and host.
- **Do Not Track and Global Privacy Control are asked twice:** the browser sends nothing, and the collector drops it if it arrives.
- **One tracker per document, outside the component.** React mounts the component again when a navigation shows a route; a tracker made by each mount lost which page was first and the time already seen (found by driving a real Chrome, not by the unit tests).

## Amendment: the daily rollups and the retention (SAG-24, 2026-11-12)

- **Table `analytics_daily`:** one row for each day, dimension and value, kept forever. The dimensions are the kind of event, the page, the class and host of the referrer, the three UTM values, the country, the region, the device and the type of a search. `events` is what a person did (a page view, a search, a step of the funnel; the times on a page are not events), `visitors` the distinct visitors of that day, and `engaged_ms` the visible time. A visitor is a hash that changes every day, so `visitors` never adds up across days: a week's visitors are not the sum of its days, and the dashboard must say so.
- **Complete days only.** The job rolls up the days that are over, oldest first, at most 7 a run, so it catches up after a stop with a small statement. The day of today is never rolled up. A day is done when it has its row of the dimension `kind`, and a day that is done is not touched again. An event is stored with the time it arrived, so once a day is over no event arrives for it, and nothing that is deleted later was left out of the rollup; the rule only protects what a restore or a backfill puts in. A day is found by its own row, not by being later than the last one done, so an older day that was never rolled up is not skipped. Running the job twice does the same thing (the rows are replaced, not added to).
- **A flood of values cannot grow a table kept forever.** Past 100 values of a dimension in a day, the rest is one row `(other)`, with its own distinct visitors. The free values (a UTM value, a referrer host) come from outside, and a script can send as many as the rate limit lets it. A real value that is `(other)` is stored with a space after it, which a value never has (UTM values are trimmed), so it cannot meet the row of the rest.
- **The salts of the visitor code older than yesterday are also deleted by this job,** in the same statement, because the deletion that happens when a salt is asked for does not run while nobody visits, and the policy says only today's and yesterday's are kept.
- **The raw events are deleted after 13 months, only those of a day that was rolled up,** a batch of 20 000 at a time, oldest first (the job runs four times a day). If the rollup is stuck, nothing is lost.
- **Where it runs:** in the second Cron Trigger (`30 */6 * * *`), which always runs and had 26 of the 50 subrequests; two statements more make 28. No new Cron Trigger (4 of the 5 of the Free plan are in use). Rolling up first and then deleting, in that order, is part of the job. Both run whether or not `ANALYTICS_ENABLED` is on: with no events they cost two small statements, and what was measured stays valid.
- **Migration `0034`** is applied by hand in production. Until it is, the two statements fail, are logged by name (`roll-up-analytics`, `prune-analytics-events`) and do not stop the other jobs of the invocation.

- Whether the contact email is enough for what article 15 of the law asks of an aviso de privacidad (the identity and the address of who handles the data, and the way to use the ARCO rights). The owner decided on 2026-11-12 to keep the email as the only contact in `/privacy`, which already says it is the address for questions and for the rights. Whether that satisfies the article was read only in the part of the law that could be read (articles 1 to 50) and is **not settled**: it needs a legal review.

## Amendment: the privacy policy (SAG-24, 2026-11-12)

`/privacy` has its own section, "Estadísticas de uso" (`privacy.stats`, Spanish and English), that says what is measured (the kind of page, where the visit came from, the time a page was visible, the type of a search, adding to the library and following, the country and region, mobile or desktop), what is not stored (the IP address, the account, the text of a search, the city, which exact title or person), how the visitor code is made (a hash with a salt that changes every day and is kept for today and yesterday), that Do Not Track and Global Privacy Control are honored, and how long things are kept (events 13 months, then daily totals with no visitor code, with no time limit). The Cloudflare Web Analytics sentences are gone, so turning that service off is part of the switch-over, and it goes **first** (edge setup, section 16): off, then the policy deployed, then `ANALYTICS_ENABLED`, so the policy never says less than what is measured. `app/routes/privacy.render.test.tsx` ties the text to the code: the months come from `analyticsRetentionMonths`, the events table has no column for an address, a city, a user or a search text, the daily totals have no visitor, and the tracker uses no cookie or browser storage. `legalUpdatedAt` is 2026-11-12.

## Amendment: the speed of the pages, Core Web Vitals (SAG-254, 2026-11-12)

Decided with the owner before it was built.

- **The library `web-vitals` 6.2.3** (Google Chrome team, Apache-2.0, about 3 KB brotli'd, last published 2026-10-05 on the npm registry; its README read 2026-11-12) measures LCP, CLS and INP with the thresholds that Google publishes. It is a new production dependency, loaded with a dynamic `import()` after the page, so it is a file of its own and not part of what a page costs to open. It is tested in Chrome, Firefox and Safari, but **CLS only exists in Chromium**, and INP needs the visitor to click or tap, so each of the three numbers can be missing.
- **One event for each page load, with the three numbers** (`kind = 'vitals'`; columns `lcp_ms`, `cls`, `inp_ms` of `analytics_events`, each empty when not measured). One write for the visit, and not three, because every write keeps the Neon compute awake (ADR-009). The table asks for at least one number and for ranges a real page cannot pass (a minute, a score of 100).
- **It belongs to the page where the visit started.** A browser measures a document and not each move inside the app. Measuring each move (`reportSoftNavs`) exists only in Chromium 151 or newer and changes how the first load is measured, so it was not chosen. A visit that starts on `/` and then moves on counts for `/`. This is also a limit of what the numbers mean: LCP is of that page, but **CLS and INP are of the whole visit**, with every move inside the app, so a visit that lands on `/` and browses ten pages puts the worst interaction of the ten under `/`. The privacy text says it is counted for the page where the visit started.
- **It is sent once, the first time the tab hides (`visibilitychange`, and `pagehide` as a way out for a browser that does not fire the first when a tab is closed).** The tracker asks the library for every change (`reportAllChanges`) and keeps the last number of each metric, so the numbers are already there before the tab hides. Seen in a real Chrome: LCP and CLS (also a CLS of 0) arrive about 0.3 s after the load, and INP at the click. This replaced a first version that sent on `pagehide` and took the final values the library gives on `visibilitychange`: when a page is left the browser fires `pagehide` first and the library's last values come after, so the event went without them (found with a real navigation, not in the unit tests). It also does not depend on the order of the listeners of the library and ours, nor on a timer that a page being closed may never run. The limit that remains: the event is sent at the first hide, so an interaction after the visitor comes back to the tab is not counted.
- **The rollup `analytics_vitals_daily`:** for each day, page and metric, the samples, the 75th percentile (the number Google asks to judge a page by, `percentile_cont(0.75)`) and how many were good, needed improvement or were poor, by the thresholds of `server/analytics/vitals.ts` (LCP 2500 and 4000 ms, CLS 0.1 and 0.25, INP 200 and 500 ms; a value equal to a threshold falls on the better side). It is made by the same statement as `analytics_daily`, kept forever, and holds no visitor. Past 100 pages a day the rest is one row `(other)`, with all their values together: the pages are ranked by how many measurements they have (the three metrics counted together), as a first cut, and the 75th percentile of the rest is over all of them. The page is never called `(other)` itself, since a path starts with a slash. The dimension `kind` of `analytics_daily` also gets a row `vitals` (the loads that were measured), which tells how much of the traffic the speed numbers cover next to `pageview`; the rows of `kind` are one for each kind and are not meant to be added up.
- **Switch and exclusions are the same:** nothing is measured with `ANALYTICS_ENABLED` off, for Do Not Track or Global Privacy Control, for a robot, or for an administrator. `/privacy` says the speed is measured and for which page (`privacy.stats.speed`), in the same pull request.
- **Migration `0035` goes before the merge:** the code writes the new columns in every insert, so a deploy before the migration would fail every event. The migration is additive (three nullable columns, a table, a wider check), and the code that is running now works with the new schema.
