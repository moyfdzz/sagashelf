## Subrequest budget of the crons (read this before adding a job)

A scheduled invocation shares **50 subrequests** (every database statement and every outgoing call); each Cron Trigger is its own invocation. The first (`0 */6 * * *`) runs the refresh of titles (about 41), Wikidata (4), the sagas sync (1 idle, 4 the first time) and the saga drafts (1): at most 49. The second (`30 */6 * * *`) deletes the old records of picture uploads (1, always) and the old messages of the contact page (1, always) and runs the next episodes (at most 23): 25. The third (`15 * * * *`) runs `announceNewEpisodes` (1) then delivers webhook events (claim 1, each event 2, clean-up 1: 20 events are 42): **43 of the 50**; with the webhooks off it does not open the database. A new job that needs more goes in an invocation of its own (the Free plan allows 5 Cron Triggers; **3 are used**) or cuts something; fold database work into an existing statement as a CTE when you can. The CPU limit of a scheduled invocation on the Free plan is 10 ms. Keep the **Neon compute hours** in mind (100 CU-hours a month, a pause after 5 minutes without a query).

## How to work (the owner's conventions)

- One ticket per branch, cut from an up-to-date `main`, e.g. `refactor/SAG-128-authorization-test`. Conventional Commits with the ticket as scope; **commitlint enforces the `SAG-N` scope, a header of at most 100 characters and body lines of at most 100 characters.** Husky hooks run lint-staged and commitlint: never `--no-verify`. If the hook rejects the message, nothing is committed: fix it and commit again. Write the message to a file in the scratchpad and `git commit -F` it, after checking the line lengths with `awk`.
- **The flow the owner expects each time:** show the plan and the decisions you need (with a recommendation for each) and wait for "sí" (usually "sí a lo recomendado", meaning every recommendation); build; run the checks; report faithfully (what was verified and what was not); **then commit, push and open the PR without asking** (standing order); watch the CI (right after `gh pr create` there are no checks for a few seconds: a background `until [ "$(gh pr checks <n> | wc -l)" -gt 3 ]` loop, then `gh pr checks <n> --watch`); tell the owner to merge (they say "ya hice merge"). After the merge: `git checkout main; git pull --ff-only`, `git branch -D <branch>` (a squash merge leaves it "not merged"), `git fetch --prune`, check the ticket in Linear, and give the owner **numbered steps to try it in production**. A ticket with several PRs stays In Progress until the last one. If the plan changes the scope of a ticket, **say so and get the owner's OK**, rename the branch before the first push, and leave a comment on the ticket (that is how SAG-120 went from "thin four actions" to "take out the one that has logic" and gave birth to SAG-128). Create tickets in Linear (English, problem, scope and "Done when") **only when the owner asks or agrees**; check `list_issues` with `query` for a duplicate first.
- Before each commit: `npm run check` (lint, format check, typecheck, tests with coverage, build). For database changes also `npm run test:integration`. For UI or routes run the e2e on the production build **like CI**, with **2 workers as CI does**: `mv .dev.vars .dev.vars.aside; rm -f build/server/.dev.vars; CI=1 npx playwright test --workers=2 > log 2>&1; mv .dev.vars.aside .dev.vars`, then confirm `.dev.vars` is back (never read its values). `CI=1` matters (without it 8 "static file carries the base headers" tests fail: not a regression). Run it in the background and do not run `npm run build` meanwhile. **Local runs with the default 8 workers had flaky tests twice** (`ERR_CONNECTION_REFUSED` or `ERR_ABORTED` at the start of the run, right after the integration tests); the CI had none in the last 7 runs. That is a hypothesis, not a fact: repeat the whole suite before saying a failure is not yours, and say so in the PR.
- **A new test must be shown to fail on the old code**: `git stash push -- <tracked source files>`, run, `git stash pop`, check the stash list is empty. For a new untracked file use **mutation checks**: a script in the scratchpad that, for each rule, replaces one exact piece of the code (asserting it appears once), runs the tests, records whether one failed, and restores the file in a `finally` (run the subprocess with `encoding="utf-8", errors="replace"`, or Windows floods the output with decoding errors). A mutation that is **missed** is a finding: it showed a test gap twice (the page cap of the lists of people). **In an integration test write the expected table by hand and do not ask the function under test.** The integration config has no `~` aliases: test a loader with mocks in `app/routes/*.test.ts` and the data layer against the real Postgres.
- **How the big refactors of SAG-121 were proven, reuse it:** (1) a throwaway vitest file in `app/routes/` copies the harness of an existing render test and writes the HTML of 100 to 150 states to a JSON file in the scratchpad (every kind of data, every error, both languages); check first that rendering twice gives the same bytes; (2) cut the code with a **script that copies line ranges from `git show HEAD:<file>`**, asserts that every range starts and ends where expected and refuses to write anything if one does not (never retype 600 lines of JSX); (3) render the same states again and `cmp` the two files: byte for byte the same; (4) delete the throwaway test; (5) compare the sizes of `build/client/assets/*.js` before and after. The same idea proved the move of `social.ts`: compare the text of every `sql` template of the old file and the new ones.
- PR with squash merge; the title becomes the squash commit and must be Conventional Commits with `SAG-N`. Use `.github/pull_request_template.md` (Summary, Changes, Verification with the checkboxes, "Not run, and why", README, **Design** (ADR-033), Notes for the reviewer). Keep the README and the ADR current **in the same PR**; a new decision gets an ADR and a line in `docs/adr/README.md` (**keep the new row as narrow as the existing ones, or Prettier reflows the whole table**).
- All visible text goes in `app/locales/es.json` (source of truth, neutral Latin American Spanish, natural in Mexico) and `en.json` with the same keys, used with `t("...")` (typed keys: a list typed `string[]` breaks `t(\`x.${item}\`)`, keep the literal union). ESLint `jsx-no-literals`forbids literal text in JSX, including a literal empty`alt`. Plurals use `_one`/`_other`; a `count`parameter makes i18next choose a plural key. Dates, numbers and lists go through`app/lib/format.ts`.
- **The look of what is pressed lives in `app/lib/ui.ts`** (`primaryButtonClass`, `secondaryButtonClass`, `dangerButtonClass`, `smallButtonClass` (26 px, too small for a phone), `secondaryLinkClass`, `tabClass`, `linkClass`, `textLinkClass`): use them.
- Security conventions: write endpoints ask the size and the `Origin` with **`checkWrite`**, rate limit with `rateLimit(getWriteLimiter(), ...)` keyed by the person, and read bodies with `server/http/body.ts`; answers with a person's data are `private, no-store` through `server/http/cache.ts`; validate with Zod (`strictObject` for forms); every query on a person's data has the user id **of the session** in its `WHERE`. The administration uses `readAdminWrite`. Saving a title by opening it (`/media/open`) needs a session and has its own limiter (ADR-035). `app/routes/write-actions.test.ts` and `read-loaders.test.ts` list every route by who may call it: a new route must be added to the right table. Env variables are read only through `server/env.ts` and `server/runtime-env.ts`. Never edit an applied migration. A table or column that holds a person's data must be in the account erasure (`server/db/erase-user.ts`) and in the export (`server/account/export.ts`). **A new file under `server/` that the integration tests import (even through another module) must be listed in `tsconfig.node.json`** (`npm run typecheck` says which, error TS6307). The list of tables in `db/constraints.integration.test.ts` grows with each new table.
- **Links to a session page** (`/library`, `/settings`, `/sign-out`, `/admin`, `/notifications`) from any other page are plain `<a href>`, never the router's `Link` (ADR-018); also a link **from** a session page to `/u/...`. `/u/...`, `/social`, `/stats`, `/recommendations` and `/sagas` are **not** session pages.
- GitHub Actions stay pinned to a full commit hash. ESLint stays on v9. Do not replace the stack. Write code that reads like the surrounding code: comments say why, in plain English.
- Report faithfully: say what was verified, what was not (and why), and never claim something works that was not tried; **do not write a number you did not count** (a PR said "55 checks" and the script had 66). Facts about third-party limits are written in an ADR with their source and date. `WebSearch` is a deferred tool (`ToolSearch` with `select:WebSearch`).
- **Look at what you build.** For a page, render it to static HTML and measure it with `playwright` at 320, 390 and 1280 px, light and dark, in both languages (`scrollWidth` against `clientWidth`, buttons at least 40 px high), and take a screenshot. For behavior with JavaScript (a modal, focus, Escape), bundle the component alone with `esbuild` and drive it in Chromium: that found a real bug in the modal before it shipped.

## Migrations are applied by hand, and you must never see the connection string

A migration that changes or deletes data (not an added nullable column) is **preceded by a Neon snapshot** that the owner takes by hand (`docs/backups.md`). The daily encrypted copy is described in `docs/backups.md`.

Migrations are **not** run by CI or by the deploy (ADR-002). An additive one is safe to apply **before** the merge, and **must** be applied before it when the deployed code reads or writes the new column or table on a common path. Commit and open the PR first, then ask the owner to apply it. If the migration adds a constraint to existing rows, ask first for a `SELECT count(*)`. The owner runs these steps in **their own PowerShell**, from the repo root, on the PR's branch:

1. In the Neon console: Connect, production branch, **Connection pooling off** (direct connection), copy the string.
2. `git fetch origin; git checkout <the branch>`, then `$s = Read-Host "DATABASE_URL" -AsSecureString` and `$env:DATABASE_URL = [System.Net.NetworkCredential]::new('', $s).Password`.
3. `npm.cmd run db:migrate` (PowerShell blocks `npm.ps1`; from the repo root).
4. `Remove-Item Env:DATABASE_URL`, even if step 3 failed.
5. Check in the Neon SQL Editor with a `SELECT column_name, data_type FROM information_schema.columns WHERE table_name = '<table>'` and ask the owner to paste only that result. Never ask for emails.

Never ask for, accept or print the connection string, the Clerk secret key, the TMDB token, a Discord webhook address or `.dev.vars` contents. The migrations applied in production are the ones in `drizzle/meta/_journal.json`; the state file says which one was the last applied. The owner's `.dev.vars` has a `DATABASE_URL` that points to a **remote** database: never run anything that writes through the app against it. The local Docker Postgres is not reachable from the running Worker (it uses Neon over HTTPS); integration tests use `pg` directly. A generated migration gets a random name: rename the file and the `tag` in `drizzle/meta/_journal.json`. **When the owner must change or delete a row by hand, look it up first** (`SELECT` by a column you know, never emails) and use `... WHERE id = '<id>' RETURNING ...` so they see how many rows changed (this session a declined request was removed that way).

## Things that went wrong before, so you avoid them

- **A lock or a ban in Clerk is not the state of our account.** `lockUser` expires (1 hour by default) and neither it nor `banUser` ends the sessions that are open. The app asks `users.moderation_status` on every request (`server/auth/require.ts`, ADR-040); anything new that reads the session must go through `requireUser`, `requireRole` or `getOptionalUser` (all three send a restricted person to `/account-restricted`), and never trust `getAuth` alone. Found on 2026-11-06 trying the moderation panel in production: the suspended person kept navigating.
- **`npm run check` stops at the first test that fails and then does not build.** An e2e run started after it runs on the old build, and its green means nothing. Look at the time of `build/server/index.js`, or chain the commands with `&&`, before trusting it. Found on 2026-11-06 on SAG-148.
- **The permission classifier blocks `rm -f "$VAR"/*.png`**, since the variable could be empty. Use the safe form `rm -f "${VAR:?}"/*.png`, or a literal path.
- **A loop of `gh pr checks` must stay under about 590 seconds**, the limit of the tool. When GitHub queues for long, the command moves to the background and its notice has to be waited for, not run again. The PRs of SAG-150 and SAG-151 took more than 15 minutes (2026-11-06).
- **The permission classifier blocks history rewrites and force-pushes even after the owner said yes in chat.** Tell the owner exactly what to type with the `!` prefix. Re-running a failed CI job with `gh run rerun <id> --failed` is allowed.
- **gitleaks flags a made-up token with high entropy**, and scans every commit of a PR. Keep every fake key in a test obviously fake and low entropy. A `grep` of the staged diff for `secret|token|password` shows harmless names (`fakeWebhookToken`, `secretKey: "x"`): read the hits.
- **The Write tool OVERWRITES an existing file without warning.** This session a new `server/db/profile.ts` replaced the profile of the account (the type check caught it before any commit, and `git checkout HEAD -- <file>` restored it). **Before creating a file, check that the path does not exist** (`ls`, `git ls-files`).
- **Backslashes are lost in a Bash heredoc**: `\n` becomes a real newline and `\b` a backspace character, in Python scripts too (it happened four times). For anything with a backslash, a regex or an escape, **write the script with the Write tool into the scratchpad and run it**, or use the **Edit tool**. The Write tool also turns a backslash-u escape of an invisible character into the character. **Never run `cat > file` without input: it hangs the shell.**
- **The Bash tool refuses a whole command when a heredoc has an unbalanced apostrophe or quote**, and then nothing in it runs. Check `git diff --stat` after a failed multi-step command.
- **A Python script that rewrites a source file must open it with `newline=""`**; the default on Windows writes CRLF. Make it safe to run twice (each patch asserts its text appears once) or it dies half way. Run Python with `-I` on anything under the repo.
- **The Edit tool needs the file to have been read** in the conversation, and Write needs it to overwrite. After `prettier --write` changes a file, read it again before editing it. A note saying a file "changed on disk" after you switch branches is just the other branch's content.
- **Stage named files** (or `git add -A -- <named paths>`), scan `git diff --staged`, commit, then check `git status --short` and `git log --oneline -1`. A path with a dollar sign (`app/routes/u.$username.tsx`) must not be typed in double quotes in the shell. Fix with a new commit, never a force-push without the owner.
- **`npm run check` fails on a formatting difference** in any file: `prettier --write` what you changed first. `react-router typegen` runs in `npm run typecheck`.
- **ESLint traps:** `jsx-no-literals`; `no-restricted-imports` forbids `react-dom/server` and **any `~server/*` import** under `app/components` and `app/lib` (and `~/*` under `server/`); `no-unused-vars`; `no-control-regex`; `jsx-a11y/*`; `no-non-null-assertion`; `no-useless-escape`; `no-irregular-whitespace`.
- **A fixture or a test can be wrong, not the code**, and a real defect can hide in a test that "fails for a silly reason". Read the failure before changing the code. Docker Postgres's clock is about 0.15 s ahead of Node's: an integration test must not mix `now()` of the database with `Date.now()` of the test. An `ON CONFLICT ... DO UPDATE ... WHERE` and a `close()` that queues an event are the kind of detail that bites: `dialog.close()` fires a `close` event **later**, so a listener attached right after it takes it for the user.
- **React Router answers a cross-site POST to a page route with a 400 before the action runs** ("The request.url origin does not match origin header": expected). A resource route reaches its own check (403). An end-to-end test of a page route must accept 400 or more.
- **A PR whose title has `SAG-N` makes Linear mark that ticket Done on merge**, even when the work is not finished (SAG-29 and SAG-135 had to be reopened). Reopen it, or plan the last PR to be the one that closes it.
- **Windows traps found in SAG-135:** `mkdir -m 700` fails in Git Bash (use `mkdir` then `chmod 700 ... || true`); PowerShell 5.1 corrupts binary data piped or redirected to a native command (use `docker cp` or `cmd /c` for a `.dump`); the owner's PowerShell does not find `gpg` (use `& "C:/Program Files/Git/usr/bin/gpg.exe"`); `host.docker.internal` reaches the local Postgres from a container; pass a secret to `docker run` with `--env NAME` (no value), never on the command line. Also: a new `.gnupg` gets `use-keyboxd` in `common.conf` and the `gpg` of Git fails to start `keyboxd`, so empty that file; that `gpg` reads no Windows path in `--homedir` (use `/c/Users/...`) and needs a short one (a long scratchpad path fails to reach `gpg-agent`); Windows PowerShell removes double quotes inside a single-quoted argument of a native command, so `sh -c 'psql "$X" -c "..."'` breaks (send the SQL through a pipe with `docker run -i`); `gpg-agent --daemon` holds an open pipe, so never pipe its output. A command that writes to production, even a check, goes inside `begin; ...; rollback;`: on SAG-135 the owner pasted the owner role's address by mistake and only the rollback kept the rows.
- **Time zones:** the owner is in Mexico City (UTC-6, no DST). Check `date` and `date -u`.
- **CSP forbids inline styles** (`style-src 'self'`): no `style=` attributes. **Tailwind generates only classes it can read whole in the code.** A very long unbroken string widens the page on a phone unless its element has `break-all` or `break-words`.
- **Anything a page loads from another origin needs a test in a real browser under the production CSP.** Profile pictures from `img.clerk.com` passed every test and were blocked in production (SAG-138): the dev server sends no CSP, a static render has none, and no e2e test drew a picture. A check of the header's text does not show this: load the resource. `e2e/security.spec.ts` has the pattern: `page.route` answers for the origin, and an `Image` in the page says whether it loaded. Run it with `CI=1` on the production build, and show that it fails with the old policy.
- **Cloudflare Workers differences found only against the real runtime:** `fetch` init `redirect: "error"` and `credentials` do not exist; the Worker's database client is Neon over HTTPS, so **a statement is the only atomic unit** (no interactive transaction): put changes that must go together in ONE statement with data-modifying CTEs; each database statement and outgoing call is a subrequest. A boolean that changes the SQL is written as SQL words, not as a bound parameter, since the Neon driver cannot be tried locally.
- **Dashboard variables are deleted by a deployment** unless `keep_vars` is set (it is). A preview deployment does not share the production session cookie, so a signed-in feature cannot be tried on a preview URL: the owner tries it in production after the merge. **Changing a variable in the dashboard also creates a deployment**, so an entry in the list of deployments is not always a build of a commit.
- **The Workers Builds check can stay queued with no build in Cloudflare.** On PR #132 GitHub kept waiting and the Cloudflare list showed no new build, during a Cloudflare incident. Look at the Cloudflare status page first. When the incident is over, an empty commit on the branch starts the build (`git commit --allow-empty`, with the usual `SAG-N` scope). It is a required check, so the PR cannot merge until then.
- **The local e2e run uses the owner's `.dev.vars`** unless you move it aside as above. A leftover `wrangler dev` or `workerd` process locks `build/server` and keeps port 4173.
- **GitHub Actions can queue for several minutes** (once for about seven) while its status page says everything is operational: wait, do not re-run.
- **Provider rules** (sources and dates are in the ADRs): Open Library about 3 requests a second; MangaDex about 5 a second, credit required; TMDB data may be kept at most 6 months; Wikidata is CC0, stop on a 429; TVmaze is CC BY-SA, at least 20 calls every 10 seconds, credited; **Discord** (ADR-029): content up to 2000 characters, a 429 has `retry_after`, and a webhook that answers 404 must not be used again.
