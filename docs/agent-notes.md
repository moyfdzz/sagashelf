# Notes for coding agents

What does not change from one session to the next. Read this before writing code. It is the core; the rest is split so a session only reads what it needs:

- **Area rules** in `.claude/rules/` (database, routes and security, UI, end-to-end tests, crons and providers, tests). Claude Code loads each one when it reads a file of that area (`paths:` at the top of each file). Another agent must open the file of the area by hand.
- **Procedures** in `.claude/skills/`: `apply-migration` (a migration in production, applied by the owner) and `browser-review` (the signed-in pages in a real browser).
- **The state of the day** is not here: it is in `CLAUDE.local.md` (ignored by git, rewritten by `/handoff`), in the ticket In Progress and in the memory folder.
- **What the owner still has to try in production** is the pinned ticket SAG-265 of `moyfdzz/sagashelf-tickets`.

Personal rules (attribution, secrets, confirmations) are in the owner's user-level `CLAUDE.md` and apply here too.

## The flow of a ticket

1. **Branch.** One ticket per branch, cut from an up-to-date `main`, e.g. `refactor/SAG-128-authorization-test`. Work happens one session at a time, so read `git status -sb` in the shared checkout and, when it is clean, `git checkout main; git pull --ff-only; git checkout -b <branch>`. Use a worktree only when another session is working at the same time (traps below).
2. **Plan.** Show the plan and the decisions you need, with a recommendation for each, and wait for "sí" (usually "sí a lo recomendado": every recommendation). **A plan first for a big change even when the owner says "empieza"**: more than about 8 files, or a decision that changes what is built (agreed 2026-11-08, after SAG-159). If the plan changes the scope of the ticket, say so, get the owner's OK, rename the branch before the first push and leave a comment on the ticket.
3. **Build and check** (next section). Report faithfully what was verified and what was not.
4. **Lessons.** If the work taught something that will still be true in a month, add it to this file or to the rule of its area **before** `gh pr create`, so it is in the first version of the PR. No filler.
5. **Commit, push and open the PR without asking** (standing order of 2026-11-04). Use `.github/pull_request_template.md` (Summary, Changes, Verification with the checkboxes, "Not run, and why", README, **Design** (ADR-033), Notes for the reviewer). Keep the README and the ADRs current in the same PR; a new decision gets an ADR and a row in `docs/adr/README.md` (**keep the row as narrow as the others, or Prettier reflows the whole table**). The title becomes the squash commit: Conventional Commits with `SAG-N`.
6. **Watch the CI.** Right after `gh pr create` there are no checks for a few seconds: a background `until [ "$(gh pr checks <n> | wc -l)" -gt 3 ]` loop, then `gh pr checks <n> --watch`. A loop must stay under about 590 seconds (the tool's limit); when GitHub queues for long it moves to the background, so wait for its notice instead of running it again. Actions can queue for minutes while the status page says all is well: wait, do not re-run. Re-running a failed job with `gh run rerun <id> --failed` is allowed.
7. **Review.** For a PR that changes code, run `/code-review` yourself (medium unless the owner asks for another level; `max` and `ultra` only when asked), check each finding against the code, fix the valid ones with more commits on the same branch, and say which ones were left and why. A docs-only PR has no review. Do not open follow-up tickets for findings of the same PR.
8. **Merge** is the owner's ("ya hice merge"). Then: `git checkout main; git pull --ff-only`, `git branch -D <branch>` (a squash merge leaves it "not merged"), `git fetch --prune`, close the ticket by hand (`gh issue close <N> --repo moyfdzz/sagashelf-tickets --reason completed`) and move its card to Done; a ticket with several PRs stays In Progress until the last one. **Add the checks of the feature to SAG-265** (one line under "Features" plus a comment with the numbered steps) instead of only writing them in the chat.
9. **One session per PR.** After the merge run `/handoff`, and start the next one in a new session ("continúa"). A long session carries the noise of old work and costs much more (each call re-reads the whole conversation). Several agents at once are not worth it here (one owner, shared files like `es.json` and `app/lib/ui.ts`); the two uses are `/code-review` and a read-only search of the whole app.

**Tickets** are issues of the private `moyfdzz/sagashelf-tickets`: create one only when the owner asks or agrees, after `gh issue list --repo moyfdzz/sagashelf-tickets --state all --search "<words>"` for a duplicate. English, with problem, scope and "Done when"; the title starts with the next number (`SAG-N: ...`, the highest issue number plus one); what only an agent needs goes in a `<details><summary>Agent notes</summary>` block. Never copy a ticket's text into this repository, a PR or a commit. **Never write "close", "closes" or "fixes" next to a ticket number**, and write a PR as `moyfdzz/sagashelf#N` inside a ticket, never a bare `#N`. The Project "SagaShelf tickets" is number 1 of the owner (`gh project ...` needs the `project` scope); its field **Status** has Backlog, In Progress and Done. Linear is no longer used (ADR-046).

**Open decisions** go in `CLAUDE.local.md` under "Waiting for the owner". Offer them at the start of a session with a recommendation. **A screenshot helps**: without the `browser-review` setup, ask the owner to paste a capture instead of guessing from the markup.

## Checks before each commit

- `npm run check` (lint, format check, typecheck, tests with coverage, build, budgets). A hook of `.claude/settings.json` formats each file that Write or Edit touches; a file changed by a script or a shell command still needs `npx prettier --write`. The check **stops at the first failing test and then does not build**, so a `test:a11y` after a failed check uses the old build.
- `npm run typecheck` also rewrites the `include` list of `tsconfig.node.json` from the imports of `db/` and `e2e/` (`scripts/sync-tsconfig-node.mjs`): commit that change with the code. In CI it only checks and names the missing file.
- Database changes: also `npm run test:integration`. It starts Docker Desktop and the local Postgres of the main checkout when they are off (`scripts/integration-db.mjs`), and a second run started while one is going is refused (an advisory lock).
- UI or routes: `npm run test:e2e:local` (the suite like CI, `.claude/rules/e2e.md`); add `--a11y` for a new page.
- **The exit code in the notice of a background task is the one of its last command.** `npm run check:full > log 2>&1; echo CHECK_EXIT=$?` says "exit code 0" even when tests failed: read the `CHECK_EXIT` line and the `Tests` lines of the log.
- **Two runs of `npm run check` at once fail on the coverage folder**, and an interrupted run can leave its `vitest` alive for a while; look for `node ... vitest.mjs` first.
- Stage named files (`git add -A -- <named paths>`, never `git add .`), scan `git diff --staged` (a `grep` for `secret|token|password` shows harmless names such as `fakeWebhookToken`: read the hits), commit, then check `git status --short` and `git log --oneline -1`. Husky runs lint-staged and commitlint: never `--no-verify`. **commitlint rejects a header over 100 characters (aim for 72) and a body line over 100**: write the message to a file in the scratchpad, check it with `awk`, and `git commit -F <file>`. If the hook rejects it, nothing was committed. Fix with a new commit, never a force-push without the owner.

## Reporting

Say what was verified, what was not and why, and never claim something works that was not tried. **Do not write a number you did not count** (a PR said "55 checks" and the script had 66). Mocked tests only prove the code against the fixtures you wrote: say so, and try the real thing when you can. The signed-in pages cannot be tried headless: give the owner numbered steps and add them to SAG-265. Facts about third-party limits go in an ADR with their source and date. GitHub Actions stay pinned to a full commit hash; ESLint stays on v9; the stack is not replaced. Code reads like the code around it, and comments say why in plain English.

## Traps of the tools on this machine

- **Bash and long commands.** A command with several heredocs, quotes, backticks or accents can fail with "unexpected EOF" and run nothing, and a heredoc loses backslashes (`\n`, `\b`, regexes). Write scripts and long texts with the Write tool into the scratchpad and run them with `node` or `python -I`; use Edit for anything with a backslash. An unbalanced quote makes the tool refuse the whole command: check `git diff --stat` after a failed multi-step command. Never run `cat > file` without input (it hangs). A `cd` carries to the next call: use absolute paths.
- `python3` does not exist in Git Bash; `python -I` does. A Python script that rewrites a source file opens it with `newline=""` (the default writes CRLF), asserts each patch appears once, and runs subprocesses with `encoding="utf-8", errors="replace"`.
- Git Bash turns an argument that starts with `/` into a Windows path (`MSYS_NO_PATHCONV=1`). A path with a dollar sign (`app/routes/u.$username.tsx`) must not go in double quotes.
- **Windows PowerShell 5.1** corrupts accents when it reads a file with `Get-Content -Raw` and writes it back (`ámbar` became `Ã¡mbar`), and corrupts binary data piped to a native command. Edit files with the Edit tool. The owner's PowerShell blocks `npm.ps1`: use `npm.cmd`.
- **The permission classifier** blocks `rm -f "$VAR"/*.png` (use `"${VAR:?}"` or a literal path), and history rewrites and force-pushes even after the owner said yes: tell the owner what to type with the `!` prefix.
- **Never undo an experiment with `git checkout -- <file>` or `git restore` on a file with uncommitted work**: it throws the work away (three times). The project settings ask the owner before either runs; copy the file to the scratchpad before the experiment and restore from the copy. `git checkout HEAD -- <file>` to restore a file a tool damaged is fine.
- Do not edit a file by line number after another edit added lines to it: match on text.
- Node cannot reach some APIs over IPv6 here (`ECONNRESET` against `api.themoviedb.org`): run a throwaway script with `node --dns-result-order=ipv4first`.
- **Worktrees** (only for parallel sessions): make the worktree first with `git worktree add .claude/worktrees/<name> -b <branch> origin/main`, then `EnterWorktree` with that path (it takes only an existing worktree); never create the branch in the shared checkout first. A new worktree has no `node_modules` (`npm ci`). The Bash tool there refuses compound `git`/`gh` commands, heredocs with `python`, and in a background job `npx` with a `$` path: one plain command per call, Write and Edit for files, a literal path for `--body-file` and `-F`. The stash is shared by every worktree, so for "fails on the old code" use `git diff --output=<path outside> -- <dir>` and `git apply`. `../../..` is the shared checkout root: write logs with absolute paths. A plain `npm run db:up` from a worktree starts a second, empty database and locks the folder (`docker rm -f` it, `docker volume rm` its `_pgdata`); `npm run test:integration` avoids it. After a squash merge use `git worktree remove` (on Windows it may leave an empty folder: `Remove-Item -Recurse -Force`) and delete the branch by hand.

## CI and deploys

- **The Workers Builds check can stay queued with no build** (PR #132, during a Cloudflare incident). Look at the Cloudflare status page; afterwards an empty commit with the usual scope starts it (`git commit --allow-empty`). It is required (ruleset `gh api repos/moyfdzz/sagashelf/rulesets/25519450`), so the PR cannot merge until then.
- **Dashboard variables are deleted by a deployment** unless `keep_vars` is set (it is). Changing a variable in the dashboard also creates a deployment. A preview deployment does not share the production session cookie, so a signed-in feature is tried in production after the merge (SAG-268 is the plan for a staging Worker).
